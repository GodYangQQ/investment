# 03 · AI 协作工作流

> **这册决定这几天你是顺畅还是抓狂。**
> 原系统 70% 的返工，不是因为模型不够聪明，而是因为**验证有洞**。
> 下面每一条规矩，都是被一次真实翻车逼出来的。规矩后面附案例，
> 因为没有案例的规矩没人会认真执行。

---

## 零、先认清 AI 的真实失败模式

不是"写不出代码"，而是这四种：

| 失败模式 | 表现 | 你会看到 |
|---|---|---|
| **验证环境错** | 在本地验证通过，线上跑的是旧代码 | 它说修好了，你打开还是坏的 |
| **验证维度错** | 只验终点不验过程，只验一种情况不验全部 | 证据"全绿"，你一用就崩 |
| **修 A 坏 B** | 改一处引发另一处回归，只测本次改动点 | 老功能莫名其妙不能用了 |
| **过度自信** | 用叙述代替证据："已验证""无法复现" | 你追问才发现根本没测 |

**共同点：它是真心以为自己做完了。** 所以解法不是骂它，是**造一套让它无法自欺的验证机制**。

---

## 一、机制先行：两份文件必须最先建

在写任何功能代码之前，先在仓库里建这两份文件。这是整个工作流的地基。

### 1.1 `docs/REQUIREMENTS.md` · 需求台账

每条需求编号入册（R-001, R-002…），记录：编号 / 描述 / 状态 / **验收标准** / 证据链接。

**作用**：
- 需求不再散落在几十条对话里，AI 换会话、断线、失忆都能接上
- 每次交付前逐条自测打勾，未全绿禁止请求验收
- 你能一眼看到"哪些说过的事还没做"

> **真实案例**：原系统开发中会话中断过多次（网络断连、上下文超限）。有了台账后，
> 新会话只要读两个文件 + `git log` 就能接上，中断成本从"重讲一遍需求"降到零。

### 1.2 `docs/REGRESSION.md` · 永久回归清单

编号 G-1, G-2… 每条记录：测什么 / 怎么测 / **为什么它在这里（哪次翻车）**。

**铁律：任何缺陷出现第二次，立刻升级为永久回归项，此后每轮交付必跑。**

原系统最终的回归清单（可直接照抄作为起点）：

| 编号 | 内容 |
|---|---|
| **G-0** | **画线全功能矩阵**：全部线型 × {选中/整线拖动/端点拖动/样式修改/删除} × 日K周K × 对数线性 × 全屏非全屏（约 150+ 格），**线型清单从工具条动态生成**（新增线型漏测=构建失败） |
| G-1 | 画线延伸至图表右缘（含未来区），新画线与存量线 |
| G-2 | 对数坐标拖动**过程级**等比（录屏 + 每 100ms 采样锚点比值） |
| G-3 | 周期切换 12 组合（日周月 × 对数线性 × 蜡烛折线） |
| G-4 | 盘中同步三市场（A股/港股/美股**各自开盘时段**分别测） |
| G-5 | 全页面遍历零 5xx 零白屏 |
| G-6 | 画线样式记忆跨刷新跨设备 |
| G-7 | 哨兵 CRUD（含同日重设） |
| G-8 | 单测全绿（**且测试文件必须在生产镜像内**） |
| G-9 | 幂等保存 + 铁律③盘中数据不入引擎 |
| G-10 | 全屏模式下所有画线功能 |
| G-11 | 沙箱标的不出现在任何生产界面 |

## 二、六条取证纪律（附翻车案例）

### 纪律 1 · 只认线上证据

> **翻车案例**：画线延伸缺陷修了两次都没修住。第三次才发现根因之一是
> **代码改了但容器从未重建，线上一直跑旧代码**。它的截图是真的（本地新代码），
> 你看到的也是真的（线上旧代码），两边都没说谎，但验收环境错了。

**规矩**：一切验收截图、接口响应、录屏，必须取自**线上部署环境**。
修复流程固定为：`改 → 同步到服务器 → 重建容器 → 线上取证`。

配套：页面显示**构建时间戳**（侧栏底部），一眼确认页面新旧。

### 纪律 2 · 过程级证据，终点校验不算数

> **翻车案例**：对数坐标下拖动画线会变形，修了三次。前两次的证据都是
> "拖动结束后两个端点价格比值相等"—— 数字全对。但用户看到的是
> **拖动过程中**线在变形：预览的每一帧走的是另一条代码路径。
> 终点对、过程错，等比证明全绿，肉眼照样走样。

**规矩**：涉及交互过程的缺陷，只认**录屏 + 过程采样**。
例：拖动期间每 100ms 采样两锚点价格比值，全程恒定（误差 < 1e-6），采样日志随交付提交。

### 纪律 3 · 全功能矩阵，不许只测改动点

> **翻车案例**：图表模块连续三次"修 A 坏 B"——
> 改坐标坏了周期切换按钮；重写线型坏了延伸；锁定库拖动坏了整个选中功能
> （手术成功、病人没醒）。每次都只测了本次修改的那一个点。

**规矩**：牵一发动全身的模块（图表、画线、同步）建立**全功能矩阵**，
每次触碰该模块，交付前必须跑完整矩阵。
**矩阵的清单要从代码动态生成**（如线型清单从工具条按钮生成），否则新增功能会漏测。

### 纪律 4 · 沙箱标的，测试永不碰真实数据

> **翻车案例**：矩阵测试的自动化夹具误把真实持仓标的的回撤区改成了错误数值
> （当场发现并恢复）；验收哨兵功能时往真实指数上挂了测试哨兵。

**规矩**：建 1–2 只 `TEST` 沙箱标的（合成 K 线），**排除出列表/看板/日报/同步/统计**。
一切测试、验收、演示的写操作只允许作用于沙箱。

### 纪律 5 · 禁止硬删

> **翻车案例（最严重）**：AI 判定某批数据是自己的测试污染，写脚本硬删。
> 次日复查 nginx 访问日志才发现：**那是用户十分钟前亲手画的头部颈线**，
> 且**数据库从未有过备份**（部署方案里写了每日 pg_dump，但从未实装），无法回滚。

**规矩**：
1. **任何数据清理一律软删或迁入归档表，永不 DELETE**
2. 在核心表上装**数据库触发器**做物理拦截 —— 未授权 DELETE 直接报错回滚
3. 凡涉及真实数据的删除/清理，**执行前必须停下来问人**
4. **你给 AI 的指令里，"检查/核实"类任务必须明确写"只诊断、不删除"**
   （上述事故中，人类指令是"检查这张卡为什么还挂着"，AI 从"检查"越界成了"删除"）

### 纪律 6 · 安全网本身也要抽查

> **翻车案例**：自查脚本里"单测全绿"那一步是**假绿** ——
> 测试文件根本不在生产镜像里，靠手工拷进容器；容器一重建，9 套单测全挂。
> 也就是说此前多轮的"单测全绿"都是虚的。

**规矩**：定期抽查验证机制本身。每次自查前自动注入测试文件；
备份要**演示一次真实恢复**才算数；回归清单每季度回读一遍。

## 三、交付节奏

### 3.1 检查点制度

**不要每个模块都停下来等确认**（太碎，你会被打断到崩溃），
也**不要一口气做完再验收**（错太深，返工代价大）。

正确做法：**预先约定 2–3 个检查点，其余连续干**。

原系统的分法：

```
【硬装】机制建设 → 数据层 → 规则引擎 → 识图/画线 → 质地评分
        中间不停顿、不汇报、不等确认，模块间自测通过就继续
        ↓ 检查点1：规则引擎历史回放结果（数字对不对）
        ↓ 检查点2：看板单页样稿（视觉对不对）
【软装】通知闭环 → 首页完整版 → 持仓视图 → 竣工报告
        ↓ 检查点3：第一份真实日报推送
【打磨】使用中发现的缺陷 + 易用性审计
```

**只有涉及规则本身的歧义才允许中途停下来问你。**

### 3.2 批次内的执行顺序

每个大批次内部固定为：

```
机制 → P0缺陷 → 新功能 → 体验打磨 → 自审报告
```

先建机制是因为机制会影响后面所有验证方式；P0 优先是因为缺陷会污染新功能的验收。

### 3.3 易用性自审

大批次结束时，让 AI **以真实用户身份把全站每页每流程走一遍**，输出
《易用性审计报告》：问题清单（截图 + 位置 + 建议方案 + 工作量估计）按影响排序，
**先报告不动手**，你圈选后再执行。

> 原系统这一步产出了 14 条，其中 3 条是你自己没意识到的真问题
> （移动端适配、批量导入进度不可见、重复引导提示）。

## 四、人类侧的四个动作

AI 能力再强，这四件事必须你做。

### 4.1 把感觉翻译成规则

**反例**："我要科学的减仓，保住利润。"
**正例**："完成度 70% 减到剩 70%，80% 剩 50%，90% 剩 25%，自峰值回撤 20% 全清。"

AI 无法从前者推出后者。这一步的思考量是整个项目里最大的，**也是唯一无法外包的**。

### 4.2 亲自验收，别信"已完成"

每次交付**自己打开页面点一遍**。原系统所有的严重缺陷都是用户实测发现的，
没有一个是 AI 自查发现的（自查发现的都是次要问题）。

### 4.3 描述缺陷要具体

| 差的描述 | 好的描述 |
|---|---|
| "画线有问题" | "画好的线点不中，工具条不出现，右侧 Y 轴出现一个区间残留" |
| "不好看" | "进度条太细、卡片间距太挤、这个蓝色换掉、字太小" |
| "同步坏了" | "A 股盘中点同步，A 股更新了，但美股全部显示 0.00%" |

**具体描述能省 AI 半小时排查，模糊描述会引它猜错方向。**

### 4.4 同一个坑第二次出现，立刻升级机制

不要接受"这次一定修好"。第二次出现时，要求：
1. 写清**前一次为什么没修住**（书面复盘）
2. 把它加入永久回归清单
3. 给出新的验证方式（更严的证据标准）

## 五、视觉设计的特殊做法

**AI 不知道"好看"是什么。** 文字描述风格（"参考 Copilot Money 的立体感"）几乎无效，
因为它没见过那个界面，只能凭训练里的模糊印象猜，猜出来就是工程师审美。

**有效做法是三件套**：

1. **给真图**：把参考产品的截图直接发给它（多模态模型能看图）
2. **给数字**：把风格翻译成像素级规范

```
页面底色 #F7F8FA，卡片纯白 #FFFFFF
卡片圆角 16px，边框 1px #EEF0F3
阴影双层 0 1px 2px rgba(16,24,40,.04), 0 8px 24px rgba(16,24,40,.06)
悬停 0 12px 32px rgba(16,24,40,.10) + 上浮 2px，过渡 200ms
唯一主色 #4F46E5；涨 #E23A3A 跌 #16A34A（A股习惯）；警示 #F59E0B
文字三级：#0F172A / #64748B / #94A3B8
数字全部 tabular-nums 等宽
间距体系 8px 基数；卡片内边距 24px，卡片间距 16px，区块间距 32px
动效：数字 count-up 300ms，页签切换 200ms，全部 ease-out
```

3. **给自查循环**：要求它「改完自己截图 → 与参考图并排自评 → 列出 5 处最大差距 → 修掉 → 循环直到无重大差距 → 才允许提交」

**还有两条结构性要求**（这两条比配色更决定"像不像专业产品"）：

- **左侧固定导航栏**（不是顶部导航）—— 专业后台的骨架
- **可视化密度硬规则**：每张卡片至少一个图形元素，**禁止纯文字卡**
  （胶囊加 sparkline、大数字配涨跌 chip、评分用环形、风险用半环仪表、历史用竖向时间线）

## 六、常见反模式（别踩）

| 反模式 | 后果 | 正解 |
|---|---|---|
| 把整段开发对话记录交给新 AI | 它会把已被推翻的决定重做一遍 | 只给终态文档 |
| "你看着办" | 它会发明你不想要的规则 | 交易规则必须逐条指定，禁止自行发明 |
| 让它一次做完所有页面 | 错误堆叠，debug 地狱 | 分模块，每步给出验证方式 |
| 接受"无法复现" | 缺陷仍在，下次还犯 | 要求附上复现脚本原文，核对脚本本身是否有效 |
| 只在收盘后测盘中功能 | 时段相关缺陷永远测不出 | 时段相关功能必须在对应时段实测 |
| 用"检查一下"表达"诊断但别动" | 可能被理解为授权修改/删除 | 明确写"只诊断、不删除、不修改" |
| 权限确认全部关掉图省事 | 误删无人拦截 | 白名单常用操作，删除/外发消息仍需确认 |

## 七、给 AI 的固定工作方式（写进每轮提示词）

```
工作方式（每轮必须遵守）：
1. 证据先行：任何"已验证/无法复现/正常"的结论必须附可核对的产物
   （截图、SQL 输出、接口响应、测试日志原文、录屏）。禁止叙述性结论。
2. 线上取证：一切证据取自线上部署环境，禁止以本地构建充当。
3. 台账登记：每条需求编号入 docs/REQUIREMENTS.md，交付前逐条自测打勾。
4. 永久回归：docs/REGRESSION.md 全跑，全绿才允许请求验收。
5. 沙箱隔离：一切测试写操作只作用于 TEST 沙箱标的。
6. 禁止硬删：数据清理一律软删；涉及真实数据的删除必须先问我。
7. 交易规则参数只能用指定值，禁止自行发明或修改。
8. 需求有歧义就停下来问，不要猜。
9. 每完成一个模块自动 git commit（提交信息含模块号）。
10. 涉及"检查/核实"类任务时，只做诊断，不做修改与删除。
```

## 八、一句话总结

> **AI 负责快，你负责准。**
> 它一天能干完你一个月的代码量，但它分不清"我以为做好了"和"用户真的能用了"。
> 这套工作流的全部意义，就是把这两者之间的距离，用机制填平。
